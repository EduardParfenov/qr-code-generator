# docker-deployment Specification

## Purpose

Сборка и запуск приложения в Docker-контейнере для production-развертывания
за nginx reverse proxy: воспроизводимый образ, декларативный запуск через
docker compose, production WSGI-сервер, конфигурация через переменные
окружения, логи в stdout.

## Requirements

### Requirement: Сборка Docker-образа

Проект ДОЛЖЕН (SHALL) содержать `Dockerfile` в корне репозитория, позволяющий
собрать самодостаточный образ приложения командой `docker build`. Образ
ДОЛЖЕН (MUST) базироваться на официальном образе Python версии 3.11 (slim-вариант),
устанавливать зависимости из `requirements.txt` и включать весь код приложения,
необходимый для запуска (`app.py`, `templates/`, `static/`). Служебные файлы
и данные (виртуальное окружение, локальные настройки `.env`, вспомогательная
папка `input/`, каталог `.git/`) НЕ ДОЛЖНЫ попадать в образ и ДОЛЖНЫ быть
исключены через `.dockerignore`.

#### Scenario: Успешная сборка образа

- **WHEN** выполняется `docker build -t qr-code-generator .` в корне репозитория
- **THEN** образ собирается без ошибок и содержит приложение со всеми зависимостями

#### Scenario: Служебные файлы не попадают в образ

- **WHEN** в рабочей копии существуют `.venv/`, `logs/`, `.env`, `input/`, `.git/`
- **THEN** собранный образ не содержит этих файлов и каталогов

### Requirement: Запуск приложения через production WSGI-сервер

Приложение в контейнере ДОЛЖНО (SHALL) запускаться через production
WSGI-сервер (gunicorn), а не через встроенный dev-сервер Flask. Контейнер
ДОЛЖЕН (MUST) принимать HTTP-запросы на порту 8000 на всех интерфейсах
(`0.0.0.0`), чтобы быть доступным для reverse proxy из общей Docker-сети.
Порт на хост НЕ ДОЛЖЕН публиковаться: наружу смотрят только порты nginx.
Количество worker-процессов ДОЛЖНО (SHALL) настраиваться переменной
окружения `GUNICORN_WORKERS` со значением по умолчанию 2.

#### Scenario: Запуск контейнера

- **WHEN** контейнер запущен и подключён к общей сети с nginx (`nginx-net`)
- **THEN** приложение отвечает на HTTP-запросы по имени контейнера
  (`http://qr-app:8000`) из этой сети, главная страница возвращает HTTP 200,
  а порт приложения на хосте недоступен

#### Scenario: Настройка количества workers

- **WHEN** контейнер запускается с переменной `GUNICORN_WORKERS=4`
- **THEN** WSGI-сервер запускается с 4 worker-процессами

### Requirement: Декларативный запуск через docker compose

Проект ДОЛЖЕН (SHALL) содержать `docker-compose.yml`, описывающий запуск
контейнера: сборку из `Dockerfile`, стабильное имя контейнера
(`container_name: qr-app`), подключение к внешней общей сети reverse proxy
(`nginx-net`, `external: true`) без публикации портов на хост, передачу
конфигурации через `env_file`, политику автоматического перезапуска
(`restart: unless-stopped`) и ротацию логов средствами Docker (logging
driver json-file с ограничением размера и числа файлов). Полный цикл
управления ДОЛЖЕН (MUST) выполняться командами `docker compose up -d`
(запуск), `docker compose logs` (логи), `docker compose down` (остановка),
`docker compose up -d --build` (обновление).

#### Scenario: Запуск одной командой

- **WHEN** в каталоге проекта на сервере выполняется `docker compose up -d`
  (сеть `nginx-net` уже создана)
- **THEN** контейнер `qr-app` собирается (при необходимости), запускается
  в фоне и отвечает на запросы по имени контейнера в общей сети, не
  публикуя портов на хост

#### Scenario: Автоматический перезапуск

- **WHEN** контейнер завершился с ошибкой или сервер перезагрузился
- **THEN** Docker автоматически перезапускает контейнер (restart: unless-stopped)

#### Scenario: Ротация логов средствами Docker

- **WHEN** объём логов контейнера достигает предела, заданного в настройках
  logging в `docker-compose.yml`
- **THEN** Docker ротирует лог-файлы (старые архивируются, лишние удаляются)
  без участия приложения

### Requirement: Конфигурация через переменные окружения

Все настройки приложения (`COMPANY_*`, `FORM_*`, `CARD_TEMPLATE_URL`)
ДОЛЖНЫ (SHALL) передаваться в контейнер через переменные окружения
(`env_file` в compose или `docker run --env-file` / `-e`). Файл `.env`
НЕ ДОЛЖЕН вшиваться в образ. При отсутствии переменных приложение ДОЛЖНО
(MUST) работать с демо-значениями по умолчанию, как и при локальном запуске.

#### Scenario: Запуск с настройками компании

- **WHEN** контейнер запускается с `env_file`, содержащим `COMPANY_NAME`
- **THEN** сгенерированная vCard содержит указанное название организации

#### Scenario: Запуск без настроек

- **WHEN** контейнер запускается без переменных окружения
- **THEN** приложение работает с демо-значениями по умолчанию без ошибок

### Requirement: Логи доступны через stdout контейнера

Приложение ДОЛЖНО (SHALL) выводить все логи (включая записи о созданных
vCard) в stdout, чтобы они были доступны штатными средствами Docker:
`docker logs <контейнер>` и `docker compose logs` (с опциями `-f`, `--tail`,
`--since`). Логи ДОЛЖНЫ (MUST) сохраняться между перезапусками контейнера
в пределах ротации Docker и НЕ ДОЛЖНЫ требовать файлов или volume'ов
внутри контейнера.

#### Scenario: Просмотр логов работающего контейнера

- **WHEN** в запущенном контейнере создана vCard и администратор выполняет
  `docker compose logs` (или `docker logs <контейнер>`)
- **THEN** в выводе видна запись уровня INFO с полным текстом vCard

#### Scenario: Логи после перезапуска контейнера

- **WHEN** контейнер перезапущен (`docker compose restart`) без пересоздания
- **THEN** накопленные логи остаются доступны через `docker logs`

### Requirement: Проверка сборки образа в CI

CI (GitHub Actions) ДОЛЖЕН (SHALL) на push в `main` и на каждый pull request
в `main` после прогона тестов выполнять сборку Docker-образа. Публикация
образа в registry НЕ ДОЛЖНА выполняться.

#### Scenario: Сломанный Dockerfile ловится до деплоя

- **WHEN** в pull request внесено изменение, при котором образ не собирается
- **THEN** CI завершается с ошибкой на шаге сборки образа

#### Scenario: Успешная сборка

- **WHEN** тесты прошли и Dockerfile корректен
- **THEN** CI успешно собирает образ и завершается зелёным

### Requirement: Документирование запуска в Docker

В `readme.md` ДОЛЖЕН (SHALL) быть раздел о запуске в Docker: создание общей
сети `nginx-net`, сборка образа, запуск через `docker compose`, передача
переменных окружения, настройка `GUNICORN_WORKERS`, пример конфигурации
nginx в контейнере (`proxy_pass` на имя контейнера приложения, файлы
`conf.d/` для размещения нескольких проектов на одном сервере), а также
раздел о логах: где они находятся (stdout контейнера, logging driver
Docker) и как их посмотреть (`docker compose logs -f`, `docker logs
--tail/--since`).

#### Scenario: Инструкция по запуску

- **WHEN** пользователь открывает раздел о Docker в `readme.md`
- **THEN** он может собрать образ, запустить контейнер через compose
  и настроить nginx reverse proxy, следуя только этой инструкции

#### Scenario: Инструкция по логам

- **WHEN** администратор открывает раздел о логах в `readme.md`
- **THEN** он может найти и просмотреть логи приложения, не заходя
  внутрь контейнера и не зная его имени
