## MODIFIED Requirements

### Requirement: Формирование vCard из данных формы

Система ДОЛЖНА (SHALL) формировать vCard, включающую: ФИО (FN), должность вместе с названием организации (TITLE), email (EMAIL), рабочий телефон (TEL тип WORK), сайт компании (URL) и рабочий адрес компании (ADR тип WORK). Добавочный телефон (TEL тип WORK) и мобильный телефон (TEL тип CELL) ДОЛЖНЫ (MUST) включаться в vCard только при заполненном значении; пустые поля `TEL` в vCard НЕ ДОЛЖНЫ (MUST NOT) добавляться.

Название организации, сайт и адрес компании являются настройками приложения и ДОЛЖНЫ (MUST) читаться из переменных окружения (`COMPANY_NAME`, `COMPANY_SITE`, `COMPANY_ADDRESS_*`, загружаемых из файла `.env` при его наличии). Если переменная не задана, система ДОЛЖНА (MUST) использовать встроенное демо-значение по умолчанию (см. readme, раздел «Настройка»).

Каждое поле vCard, значение которого может содержать текст, ДОЛЖНО (MUST) сопровождаться явным параметром `CHARSET=UTF-8`, независимо от того, содержит ли конкретное значение кириллицу. Требование распространяется на все поля: `FN`, `TITLE`, `ADR`, `EMAIL`, `URL` и каждый добавляемый `TEL` (рабочий, добавочный, мобильный). Набор полей vCard, их имена, порядок и типы `TEL` при этом НЕ ДОЛЖНЫ (MUST NOT) изменяться: изменение касается только набора параметров у строк.

#### Scenario: Генерация vCard с полным набором данных

- **WHEN** пользователь отправляет форму с заполненными полями: ФИО, должность, email, рабочий телефон, добавочный телефон, мобильный телефон
- **THEN** система формирует валидную vCard, содержащую все перечисленные данные, при этом должность дополняется названием организации

#### Scenario: Генерация vCard с обязательными полями

- **WHEN** пользователь отправляет форму с заполненными обязательными полями (ФИО, должность, email, рабочий телефон) и пустыми необязательными (добавочный, мобильный)
- **THEN** система формирует vCard с обязательными данными; поля добавочного и мобильного телефонов в vCard отсутствуют

#### Scenario: Необязательный телефон заполнен

- **WHEN** пользователь заполнил мобильный телефон, а добавочный оставил пустым
- **THEN** vCard содержит мобильный телефон (TEL тип CELL) и не содержит поле добавочного

#### Scenario: Данные компании из .env

- **WHEN** в `.env` заданы переменные `COMPANY_NAME`, `COMPANY_SITE`, `COMPANY_ADDRESS_*` и пользователь генерирует vCard
- **THEN** vCard содержит название организации, сайт и адрес из `.env`, а не встроенные демо-значения

#### Scenario: Запуск без .env

- **WHEN** файл `.env` отсутствует и пользователь генерирует vCard
- **THEN** vCard содержит встроенные демо-значения, приложение работает без ошибок

#### Scenario: Кодировка объявлена на каждом текстовом поле

- **WHEN** система сформировала vCard, в которой присутствуют `FN`, `TITLE`, `ADR`, `EMAIL`, `URL` и хотя бы один `TEL`
- **THEN** каждая строка этих полей содержит параметр `CHARSET=UTF-8`, в том числе `EMAIL`, `URL` и `TEL`, даже если их значения состоят только из латинских символов и цифр

#### Scenario: Кодировка объявлена на необязательных телефонах

- **WHEN** заполнены добавочный и мобильный телефоны, и оба содержат кириллицу
- **THEN** каждая из двух записей `TEL` сопровождается параметром `CHARSET=UTF-8`

## ADDED Requirements

### Requirement: Сохранение кириллицы при передаче в QR-код

Система ДОЛЖНА (SHALL) передавать текст vCard в QR-код без искажений: сериализованная vCard ДОЛЖНА (MUST) кодироваться в QR как UTF-8-байты в byte-режиме, чтобы многобайтовые последовательности кириллицы не подменялись и не переводились в другой алфавит. Каждая строка vCard ДОЛЖНА (MUST) укладываться в предел длины, установленный форматом vCard 3.0 (не более 75 октетов на строку), а перенос длинной строки ДОЛЖЕН (MUST) выполняться корректным переносом, допускающим восстановление исходного значения при чтении.

Значения полей с кириллицей ДОЛЖНЫ (MUST) переживать round-trip: vCard, сформированная системой, ДОЛЖНА (MUST) разбираться обратно в парсер vCard без потери символов, причём кириллица в `FN`, `TITLE`, `ADR`, `EMAIL`, `URL` и `TEL` ДОЛЖНА (MUST) читаться в исходном виде.

#### Scenario: Кириллица в значении каждого поля

- **WHEN** в `FN`, `TITLE`, `ADR`, `EMAIL`, `URL`, `TEL` и `COMPANY_SITE` заданы значения с кириллицей, и vCard разбирается обратно парсером
- **THEN** кириллица во всех этих полях читается в исходном виде, без замен, потери символов и искажений переноса

#### Scenario: Байты QR совпадают с байтами vCard

- **WHEN** система кодирует сформированную vCard в QR-код
- **THEN** QR-код содержит те же UTF-8-байты, что и сериализованная vCard, без потерь и без преобразования кириллицы в латиницу

#### Scenario: Длинное значение с кириллицей корректно переносится

- **WHEN** значение поля (например, должность вместе с длинным названием организации) содержит кириллицу и превышает длину строки vCard
- **THEN** строка разбивается переносом на строки не длиннее 75 октетов, перенос не разрывает многобайтовые символы, а обратная сборка строк восстанавливает исходное значение

#### Scenario: Перенос кириллицы в длинном названии организации

- **WHEN** в `.env` задано длинное кириллическое `COMPANY_NAME` и формируется vCard
- **THEN** строка `TITLE` в vCard не превышает 75 октетов, содержит `CHARSET=UTF-8`, а значение после разбора строки обратно парсером совпадает с исходным названием организации
