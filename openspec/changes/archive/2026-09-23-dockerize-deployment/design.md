# Дизайн: переход на развертывание в Docker

## Context

Мотивация и объём — в `proposal.md`. Текущее состояние: приложение — один
модуль `app.py`, запускается через `python app.py` (dev-сервер Flask с
параметрами `FLASK_DEBUG`/`FLASK_HOST`/`FLASK_PORT` из `.env`). Зависимости
зафиксированы в `requirements.txt`, Python 3.11.1 (`.python-version`).
Логирование настроено через `logging.basicConfig` с единственным обработчиком
`RotatingFileHandler` → `logs/info.log` (директория создаётся при старте).
Целевой сервер: физическая машина с nginx, на которой будет несколько
проектов, каждый — в своём контейнере на своём порту хоста; важно
однообразие эксплуатации между проектами.

Ограничения: backend остаётся в `app.py` (не раздуваем архитектуру);
локальная разработка (`python app.py` + venv) должна продолжать работать;
комментарии и документация — на русском.

## Goals / Non-Goals

**Goals:**

- `Dockerfile` в корне, собирающий самодостаточный production-образ.
- `docker-compose.yml` — декларативный и воспроизводимый запуск
  (порт, env_file, restart-политика, ротация логов Docker).
- Запуск в контейнере через gunicorn: `0.0.0.0:8000`, workers из
  `GUNICORN_WORKERS` (по умолчанию 2).
- Конфигурация — только переменные окружения; `.env` в образ не входит.
- Логи — только stdout; ротация и хранение — средствами Docker.
- CI дополнительно собирает образ после тестов (без публикации).

**Non-Goals:** см. proposal.md (без registry, без системы сбора логов,
без настройки реального nginx, без изменения поведения приложения).

## Decisions

### 1. Gunicorn как WSGI-сервер, а не dev-сервер Flask

Nginx не исполняет Python и не говорит по WSGI — ему нужен backend, которому
можно проксировать запросы. Dev-сервер Flask (Werkzeug) однопоточный и сам
предупреждает, что не для production.

**Альтернативы:** uWSGI (тяжелее в настройке), waitress (рабочий, но менее
распространён для Flask), nginx Unit (экзотика). Выбран gunicorn — стандарт
для Flask, одна строка запуска: `gunicorn -b 0.0.0.0:8000 app:app`.

Точка входа: `app:app` (модуль `app.py`, объект `app`). Блок
`if __name__ == '__main__':` при импорте gunicorn'ом не выполняется, поэтому
локальный запуск `python app.py` не затрагивается.

### 2. Порт 8000 внутри контейнера, доступ — только через общую сеть

Внутри контейнера фиксируем стандартный для gunicorn порт 8000. Порт на
хост **не публикуется**: nginx сам работает в контейнере и обращается к
приложению по имени контейнера (`http://qr-app:8000`) через общую внешнюю
сеть `nginx-net`. Это стандартная схема «единый reverse proxy перед
несколькими проектами»: наружу смотрят только порты nginx (80/443), до
приложений нельзя достучаться в обход nginx, и не нужно следить за
свободными портами хоста — проекты различаются именами контейнеров, а не
портами. `EXPOSE 8000` в Dockerfile — как документация. Переменные
`FLASK_HOST`/`FLASK_PORT` в контейнере не используются (они для
dev-сервера); в readme это отражаем.

### 3. Многослойный Dockerfile на python:3.11-slim (без multi-stage)

Базовый образ — `python:3.11-slim` (Debian, glibc). Alpine не подходит:
musl libc ломает бинарные manylinux-колёса, Pillow пришлось бы компилировать
из исходников с build-зависимостями — сборка медленнее, образ на практике
не меньше, плюс тонкие баги musl (DNS, локали). Distroless — избыточен
(нет shell для отладки, нужен multi-stage). Полный `python:3.11` не нужен:
компилировать нечего.

Порядок слоёв — от редко к часто меняющимся: сначала `requirements.txt` +
`pip install` (слой кэшируется), затем копирование кода.

Дополнительно: `ENV PYTHONUNBUFFERED=1` (логи сразу в stdout, критично для
`docker logs`), `ENV PYTHONDONTWRITEBYTECODE=1`.

Каркас Dockerfile:

```dockerfile
FROM python:3.11-slim
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
COPY templates/ templates/
COPY static/ static/
EXPOSE 8000
CMD ["sh", "-c", "gunicorn -b 0.0.0.0:8000 -w ${GUNICORN_WORKERS:-2} app:app"]
```

### 4. Workers через переменную `GUNICORN_WORKERS`, по умолчанию 2

Нагрузка небольшая (внутренний инструмент), поэтому 2 workers достаточно;
значение настраивается без пересборки образа. Формула `(2 × CPU) + 1`
не применяется — избыточна. `CMD` через `sh -c`, чтобы подстановка
`${GUNICORN_WORKERS:-2}` работала. Приложение stateless (генерация в памяти),
несколько workers безопасны.

### 5. docker-compose.yml — однообразие и воспроизводимость запуска

Хотя для одного контейнера compose не обязателен, он фиксирует команду
запуска в файле под git: порты, env_file, restart-политика, ротация логов.
Это удобство, воспроизводимость и самодокументирование; запуск/остановка/
обновление сводятся к `docker compose up -d` / `down` / `up -d --build`.
Принято так же, как будут оформляться другие проекты на сервере.

Каркас compose:

```yaml
services:
  app:
    build: .
    container_name: qr-app    # стабильное имя для proxy_pass в nginx
    env_file: .env
    restart: unless-stopped
    networks:
      - nginx-net             # общая сеть с nginx; порты на хост не публикуем
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

networks:
  nginx-net:
    external: true            # создаётся один раз: docker network create nginx-net
```

`restart: unless-stopped` — обязателен для прода: контейнер поднимается
после перезагрузки сервера и после падения. `container_name` фиксирует имя,
по которому nginx обращается к приложению (без него compose добавляет
префикс проекта, и имя в `proxy_pass` становится хрупким).

### 6. Логи только в stdout, ротация — средствами Docker

Файловые логи внутри контейнера — антипаттерн (живут и умирают с контейнером,
ротацию делает приложение). Принятый подход: приложение пишет в stdout,
дальше логами заведует Docker (logging driver json-file с ротацией,
настроенной в compose — прямая замена «1 МБ × 3», только на уровне
платформы). Бонус: однообразие с другими проектами — все логи смотрятся
через `docker logs` / `docker compose logs`.

Изменения в `app.py`: удаляются `RotatingFileHandler`, `os.makedirs("./logs")`
и импорт `logging.handlers`; в `logging.basicConfig` остаётся
`logging.StreamHandler()` (явно, чтобы формат и уровень были заданы в одном
месте). Формат сообщений не меняется. При локальном запуске логи идут
в консоль — для разработки это удобнее файла.

Просмотр логов (уйдёт в readme): `docker compose logs -f`,
`docker compose logs --tail 100 --since 1h`, выгрузка аудита —
`docker compose logs > audit.txt`.

### 7. `.dockerignore` — зеркало `.gitignore` по служебным путям

Исключаем: `.git/`, `.venv/`, `__pycache__/`, `.pytest_cache/`, `logs/`,
`.env`, `input/`, `openspec/`, `.github/`, `.opencode/`. Так как Dockerfile
копирует только `app.py`, `templates/`, `static/`, `.dockerignore` — вторая
линия защиты (быстрый контекст сборки, невозможность случайно утащить `.env`).

### 8. CI собирает образ после тестов, без публикации

В существующий job в `.github/workflows/ci.yml` после шага pytest добавляется
шаг `docker build .`. Это ловит сломанный Dockerfile/зависимости на PR,
а не во время деплоя. Публикация в registry не нужна: образ собирается
на сервере из исходников (`docker compose up -d --build`).

### 9. Пример nginx в readme, а не в репозитории

Реальный конфиг nginx живёт на сервере вне репозитория (единый nginx в
контейнере, конфиги проектов — в `conf.d/`). В readme даём пример
`conf.d/qr.conf` с `proxy_pass http://qr-app:8000;` и стандартными
заголовками (`Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`),
плюс нюансы эксплуатации: nginx резолвит имя при старте (приложения должны
быть запущены до старта/reload nginx), после правки `conf.d/` нужен
`nginx -s reload`.

## Risks / Trade-offs

- **Файл `logs/info.log` исчезает** — меняется привычный способ чтения
  аудита vCard. → Митигация: `docker compose logs` + раздел в readme;
  выгрузка `docker compose logs > audit.txt`; старые архивы логов на
  сервере сохраняются.
- **Логи теряются при пересоздании контейнера** (`docker compose down` +
  `up`) — json-file хранит логи в разрезе контейнера. → Митигация: ротация
  10 МБ × 3 даёт запас истории между пересозданиями; для долговременного
  аудита в будущем — система сбора логов (вне объёма); пересоздание —
  редкая операция (обновление версии).
- **`.env` случайно попадёт в образ** (секреты компании). → Митигация:
  Dockerfile копирует файлы явно + `.dockerignore` исключает `.env`;
  требование закреплено в спеке со сценарием; CI-сборка даёт лишнюю
  точку проверки.
- **Новая зависимость gunicorn** попадёт и в локальное venv. → Не вредит
  локальной разработке; dev-запуск по-прежнему через `python app.py`.
- **Тест ротации логов** (`test_log_handler_has_rotation`) станет
  неактуальным. → Заменяется на тест наличия StreamHandler и записи
  в stdout; набор тестов не уменьшается.

## Migration Plan

1. Обновить `requirements.txt` (gunicorn), добавить `Dockerfile`,
   `.dockerignore`, `docker-compose.yml`, упростить логирование в `app.py`,
   обновить тесты, документацию, CI — одним релизом.
2. На сервере: `docker network create nginx-net` (один раз),
   склонировать/обновить репозиторий, положить `.env`,
   `docker compose up -d --build`, добавить `conf.d/qr.conf` в nginx
   (в контейнере, в той же сети) и перечитать конфиг (`nginx -s reload`).
3. Старые `logs/info.log*` на сервере сохранить как архив; новые логи —
   через `docker compose logs`.
4. Откат: прежний способ (venv + `python app.py`) продолжает работать —
   код приложения обратно совместим (кроме отсутствия файла логов);
   достаточно переключить nginx обратно.
