# Design: add-container-healthcheck

## Context

Мотивация и границы — в `proposal.md` (разделы Why и Non-goals). Здесь только то
текущее состояние и ограничения, которые определяют техническое решение.

Контейнер `qr-app` работает, `nginx` обращается к нему по имени контейнера в общей
сети `nginx-net`; порт 8000 наружу не публикуется (`docker-compose.yml:19`).
Gunicorn запускается командой `Dockerfile:24` без `--access-logfile`.

Проверено на живом контейнере (`docker exec`, read-only):

| Факт | Результат |
|---|---|
| `curl` в образе `python:3.11-slim` | отсутствует (`command -v curl` пусто) |
| `GET http://127.0.0.1:8000/` через `urllib.request` | HTTP 200, **9.2 мс**, 4035 байт |
| access-лог gunicorn | не пишется: в `docker logs` только строки vCard и `Booting worker` |
| версия gunicorn | 23.0.0 (совпадает с `requirements.txt`) |
| проверка при остановленном приложении | ненулевой код возврата, `Errno 111` |

Тайминги health check измерены отдельно на временных контейнерах `alpine` с
параметрами из задачи 1.1 (`interval: 30s`, `timeout: 5s`, `retries: 3`,
`start_period: 10s`), Docker 28.4.0:

| Наблюдение | Измерено |
|---|---|
| первая проба при `start_period: 10s` | на 5-й секунде (не на 10-й) |
| `(health: starting)` при успешной пробе | до 6 с |
| переход в `unhealthy` при всегда падающей пробе | ~70 с (стабильно, три запуска) |

Первая проба на 5-й секунде объясняется тем, что внутри `start_period` Docker
выполняет пробы с интервалом `start_interval` (по умолчанию 5 с, начиная с
Docker 25). Поэтому окно `(health: starting)` — это `start_period`, а не
`interval`; заявленные в `proposal.md` «~30 секунд» завышены втрое, на
эксплуатацию это не влияет, но цифру стоит знать при чтении инструкций.

## Goals / Non-Goals

**Goals:**

- Блок `healthcheck` в `docker-compose.yml`, который Docker опрашивает изнутри
  контейнера, а `docker ps` отражает как `(healthy)` / `(unhealthy)`.
- Команда проверки без новых пакетов в образе и без публикации порта на хост.
- Явный код возврата: `0` — приложение отвечает, ненулевой — не отвечает или
  вернул ошибку.
- Явный таймаут на стороне Python меньше таймаута пробы, чтобы проверка
  завершалась кодом возврата, а не убивалась демоном.

**Non-Goals:**

- Не расширять `proposal.md` — все продуктовые исключения перечислены там.
- Не добавлять `start_interval` как отдельный ключ (объяснение — решение 5).
- Не менять `Dockerfile`, `app.py`, зависимости и `.env.example` (наблюдение про
  `GUNICORN_WORKERS` вынесено за пределы change).

## Decisions

1. **Проверять существующий `GET /`, а не добавлять `/healthz`.**
   Измерено: 9.2 мс, внешних зависимостей нет. Выделенный эндпоинт дал бы более
   слабый сигнал — статичный «ok» остался бы `healthy` при сломанном `.env`, когда
   генерация карточек не работает, потому что `GET /` читает `FORM_*` через
   контекстный процессор (`app.py:29`) и упал бы на этом же.
   _Альтернатива:_ `HEALTHCHECK` в `Dockerfile` вместо `docker-compose.yml` —
   отвергнута: конфигурация запуска в проекте живёт в compose (там же `env_file`,
   `restart`, `logging`), а `Dockerfile` отвечает только за образ.

2. **Форма `test`: список `["CMD", "python", "-c", "..."]`, не строка.**
   Строковая форма заставляет compose обернуть команду в `/bin/sh -c`, а в коде
   Python есть кавычки — двойное экранирование в YAML. Список передаёт `python -c`
   напрямую, без shell и без лишнего уровня цитирования.
   _Альтернатива:_ `CMD-SHELL` — отвергнута по той же причине; в образе нет
   `curl`/`wget`, а писать отдельный скрипт в образ ради одной строки — лишний
   артефакт сборки.

3. **Таймаут 3 секунды внутри `urlopen`, при `timeout: 5s` у пробы.**
   Без явного таймаута зависший сокет держит пробу до 5 с, и Docker убивает
   процесс пробы по своему таймауту — результат тот же (провал), но без кода
   возврата, и в логах видно обрыв, а не отказ. С запасом в 2 с успешный ответ
   (9 мс) успевает превратиться в `0` даже при задержке входа.
   _Альтернатива:_ полагаться только на `timeout` Docker — отвергнута: демон
   не даёт узнать, был ли это отказ соединения или зависание процесса.

4. **Адрес `127.0.0.1`, а не `localhost`.**
   Gunicorn слушает `0.0.0.0` (только IPv4, `Dockerfile:24`), а `localhost`
   внутри контейнера может резолвиться в `::1` первым и давать отказ соединения
   на живом приложении — то есть ложный `unhealthy`.
   _Альтернатива:_ проверять себя по имени контейнера `http://qr-app:8000/` —
   отвергнута: проверка не должна зависеть от DNS и сети `nginx-net`, которые
   создаются вручную на сервере; при их отсутствии контейнер был бы здоров по
   формальным причинам.

5. **Не задавать `start_interval` явно.**
   Внутри `start_period` Docker опрашивает контейнер каждые 5 с (дефолт
   `start_interval`) — проверено: первая проба проходит на 5-й секунде при
   `start_period: 10s`. Явное значение сделало бы поведение одинаковым на любой
   версии Docker, но добавило бы шестой ключ в конфигурацию ради параметра,
   который в образе не используется.
   _Альтернатива:_ `start_period: 0` (по умолчанию) — отвергнута: без стартового
   окна первые пробы на подъёме gunicorn попали бы в счётчик отказов, и на
   медленном сервере контейнер мигнул бы `unhealthy` при нормальном старте.

6. **`retries: 3` при `interval: 30s` = обнаружение зависания за ~70 с.**
   Измерено: пробы на 5-й и 10-й секундах (окно `start_period`), затем каждые
   30 с; третий отказ — на 70-й секунде. Для эксплуатации это приемлемо: зависание
   обнаруживается за минуту с небольшим запасом, а ложных срабатываний на живом
   приложении нет (9 мс против таймаута 5 с).
   _Альтернатива:_ `interval: 10s` — отвергнута: проверка каждые 10 секунд ради
   той же минуты ожидания добавляет лишние пробу на каждый контейнер, а выигрыша
   во времени обнаружения нет.

## Risks / Trade-offs

- **Ложный `unhealthy` на живом приложении** → проба идёт по `127.0.0.1` мимо
  IPv6 и с трёхсекундным таймаутом при ответе за 9 мс; запас по времени
  двукратный.
- **Проверка нагрузкой на приложение** → 1 проба в 30 с по рендеру главной
  страницы; это ~0.03% времени процесса, отдельная нагрузка на QR не создаётся.
- **Зависание обнаруживается, но не устраняется** → `restart: unless-stopped`
  срабатывает только по выходу контейнера, поэтому `unhealthy` — сигнал
  администратору, а не автоперезапуск. Это осознанная граница (proposal.md,
  Non-goals), а не дефект.
- **Нет истории проверок** → Docker хранит только последний результат; расследование
  прошлых инцидентов потребует внешнего мониторинга. Зафиксировано в proposal.md.
- **`docker ps` без поддержки health** → на старых версиях Docker статус не
  показывается; на сервере проекта Docker 28.4.0, требований к минимальной версии
  в проекте нет.

## Migration Plan

1. Добавить блок `healthcheck` в сервис `app` (`docker-compose.yml`), рядом с
   `restart`.
2. `docker compose config` — файл разбирается, в выводе видны все пять ключей.
3. `docker compose up -d --build`, дождаться `(healthy)`; откат — `docker compose
   down` и удаление блока, состояние приложения при этом не меняется.
4. Правки в `DEPLOY.md` (комментарий в проверке `docker ps`) и `backlog.md`
   (пункт в «Архивировано»).

Приложение не перезапускается логически: `app.py`, `Dockerfile` и зависимости не
меняются, откат ограничен одним файлом конфигурации.
