# Design: bootstrap-project

## Context

Приложение работает, но не имеет формальных спецификаций. Это изменение — документирующее: код не меняется, описывается текущее наблюдаемое поведение (см. proposal.md — Why). Единственные технические решения касаются организации спецификаций и инфраструктурных файлов.

## Goals / Non-Goals

**Goals:**

- Спецификации описывают наблюдаемое поведение, а не реализацию (без имён функций и библиотек в требованиях).
- Каждая capability — отдельный файл `specs/<capability>/spec.md` в плоской структуре (без вложенных доменов).
- Инфраструктурные файлы (`AGENTS.md`, `VERSION`, `CHANGELOG.md`, `backlog.md`) дают агенту и разработчику полный контекст проекта.

**Non-Goals:**

- Изменение поведения приложения (рефакторинг, новые фичи, тесты).
- Вложенная иерархия capabilities (`domain/capability`) — проект мал, плоская структура достаточна.

## Decisions

1. **Три capabilities: `vcard-generation`, `qr-code-generation`, `web-interface`.**
   Границы проведены по ответственности слоёв потока данных: формирование данных (vCard) → кодирование и композиция (QR + фон) → взаимодействие с пользователем (веб-страница).
   _Альтернатива:_ одна общая capability `contact-qr` — отвергнута: изменения в веб-интерфейсе (например, валидация формы) не должны затрагивать спецификацию vCard и наоборот.

2. **Поведение фиксируется «как есть», включая спорные места.**
   Например: пустые добавочный/мобильный телефоны попадают в vCard пустыми полями — это зафиксировано в спецификации, а не исправлено. Исправления пойдут отдельными changes из `backlog.md`.
   _Альтернатива:_ сразу «причесать» поведение — отвергнута, это смешало бы фиксацию с изменением.

3. **Версия 1.0.0 как стартовая.** Приложение заявлено автором как «готовое к использованию» (git log), поэтому baseline — мажорная версия. Далее — semver.

4. **Контекст проекта продублирован в `openspec/config.yaml` (`context`).** Это штатный механизм OpenSpec: контекст автоматически показывается агенту при создании артефактов.

## Risks / Trade-offs

- [Спецификации закрепят спорное поведение (пустые поля телефонов, хардкод компании)] → Осознанно: baseline фиксирует факты; изменения оформляются отдельными proposals из backlog.
- [Файлы документации могут рассинхронизироваться с кодом] → Правило в AGENTS.md: любое изменение поведения — только через OpenSpec change, при архивации спеки синхронизируются.

## Migration Plan

Не требуется: код приложения не изменяется. Откат — удаление добавленных файлов и каталога `openspec/changes/bootstrap-project/`.
